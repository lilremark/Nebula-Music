# Nebula v2.4.0 Cross-Platform Release Design

## Scope

Prepare and publish Nebula v2.4.0 as one stable GitHub Release containing
native Windows x64 and macOS arm64 artifacts. Add a reproducible GitHub Actions
release workflow and make the unsigned macOS updater check for new releases
without attempting an unreliable automatic self-install.

This release remains unsigned on both platforms. Apple Developer ID and Windows
code-signing credentials are not available.

## Current State and Problems

- GitHub's latest release is v2.3.4 and contains Windows artifacts only.
- The merged code declares `2.4.0` in `package.json` and README, but
  `package-lock.json`, `constants.ts`, the in-app changelog, and `SECURITY.md`
  still identify older versions.
- Releases are documented as a manual Windows-only `electron-builder` command.
  There is no checked-in workflow that builds both native platforms.
- Windows electron-updater consumes `latest.yml` and can automatically install
  an unsigned NSIS update, subject to SmartScreen warnings.
- macOS packaging correctly produces a DMG, ZIP, blockmaps, and
  `latest-mac.yml`, but the current updater enables automatic download and
  `quitAndInstall()` for every packaged build. An unsigned macOS app cannot
  reliably or safely self-replace through the normal signed update path.

## Release Version Contract

The stable release is `2.4.0` and the Git tag is `v2.4.0`.

Before tagging, synchronize the version and user-facing release notes in:

- `package.json`
- `package-lock.json`
- `constants.ts` (`APP_VERSION` and the top `CHANGELOG` entry)
- `README.md`
- `SECURITY.md`

`context/StreamDeckBridgeContext.tsx` continues deriving its protocol version
from `APP_VERSION`; no duplicate literal is introduced. Docker documentation is
not changed because this release does not publish a new Docker image.

A release validation script must fail when the tag, package version, lockfile
version, and `APP_VERSION` differ.

## GitHub Actions Architecture

Add `.github/workflows/release-desktop.yml`.

### Triggers and Permissions

- Push of a `v*` tag.
- Manual dispatch for validating the workflow without publishing a stable
  release.
- `contents: write` only for the final release job. Build and verify jobs use
  read-only contents permission.
- Node 24, matching the repository's existing verification workflow.

The tag-triggered workflow validates that `GITHUB_REF_NAME` is exactly
`v${package.version}` before any packaging job runs.

### Verify Job

Run on Ubuntu using `npm ci`:

- version consistency validator
- `npm run typecheck`
- `npm test`
- `npm run build`
- `npm audit --audit-level=high`

The existing high advisory for dev-only `nanoid@3.3.16` must be resolved or
explicitly removed by a safe lockfile-only patch before the release workflow is
considered green. The release workflow must not silently ignore high findings.

### Windows Job

Run on `windows-latest` after verification:

- `npm ci`
- `npm run dist:win`
- validate that all required v2.4.0 assets exist
- upload a workflow artifact containing:
  - `Nebula-2.4.0-setup.exe`
  - `Nebula-2.4.0-setup.exe.blockmap`
  - `Nebula-2.4.0-setup.appx`
  - `latest.yml`

`latest.yml` is the Windows automatic-update contract and must identify
version `2.4.0` and the NSIS installer/blockmap.

### macOS Job

Run on `macos-latest` after verification:

- `npm ci`
- `npm run dist:mac`
- verify the packaged executable is arm64 and the bundle version is `2.4.0`
- validate that all required assets exist
- upload a workflow artifact containing:
  - `Nebula-2.4.0-arm64.dmg`
  - `Nebula-2.4.0-arm64.dmg.blockmap`
  - `Nebula-2.4.0-arm64.zip`
  - `Nebula-2.4.0-arm64.zip.blockmap`
  - `latest-mac.yml`

The ZIP is the primary electron-updater payload. `latest-mac.yml` must identify
version `2.4.0`, reference the ZIP and DMG by exact name, and contain their
generated SHA-512 values and sizes. The DMG is the user-facing manual installer.

### Draft Release Job

Run after both native jobs succeed:

- download both workflow artifacts into one directory
- fail if any required asset is missing or duplicated
- parse both update metadata files and verify version, referenced filenames,
  sizes, and corresponding uploaded files
- create or update one draft GitHub Release tagged `v2.4.0`
- upload all Windows and macOS files to that draft
- generate release notes from commits since v2.3.4, then add explicit unsigned
  Windows/macOS installation caveats and the macOS manual-update limitation

Native jobs always build with `--publish never`; only the release job writes to
GitHub Releases. This prevents two jobs racing to create or partially publish a
release.

## Updater Modes

### Shared State

Extend `UpdaterState` with an explicit install mode:

```ts
type UpdateInstallMode = 'automatic' | 'manual';
```

The mode is visible through the existing preload/platform updater boundary.
Do not infer capability in renderer components from `process.platform`.

### Windows Automatic Mode

Packaged Windows builds use `automatic` mode:

- `autoDownload = true`
- `autoInstallOnAppQuit = true`
- checking, available, downloading, downloaded, and error states continue to
  broadcast
- downloaded updates retain Restart & Install behavior
- startup and user-triggered checks consume the public release's `latest.yml`

### Unsigned macOS Manual Mode

Packaged macOS builds use `manual` mode:

- `autoDownload = false`
- `autoInstallOnAppQuit = false`
- `checkForUpdates()` still consumes `latest-mac.yml`
- available, not-available, and error states broadcast normally
- downloading/downloaded/Restart & Install are not presented as available

When a newer macOS version is available:

- the title-bar update button becomes `Download Nebula <version>`
- Settings shows a matching manual-download action and explanatory copy
- invoking either action crosses a dedicated updater IPC method
- the main process constructs the canonical
  `https://github.com/lilremark/Nebula-Music/releases/tag/v<version>` URL from
  the updater's validated version and opens it externally
- renderer-provided URLs are never accepted by this IPC method

The existing downloaded update banner remains automatic-mode-only.

Future signed macOS releases can switch the main-process mode to `automatic`
after Developer ID signing and notarization are configured and verified.

## Updater Interfaces and Data Flow

1. `electron/main.ts` selects updater mode: Windows automatic, unsigned macOS
   manual, development/web disabled.
2. `createUpdater` configures the injected driver according to mode and emits
   state containing that mode.
3. Existing preload and platform APIs expose state/check/install behavior.
4. Add `updater.openDownloadPage()` through IPC/preload/platform. It succeeds
   only in manual mode with a validated available version.
5. `MacTitleBar`, Settings, and `UpdateBanner` derive actions from updater mode
   and phase rather than operating-system checks.

This keeps renderer UI independent from electron-updater and prevents external
URL input from crossing into the main process.

## Error Handling

- Any verify or native build failure prevents draft creation.
- Missing or inconsistent artifacts fail before upload.
- Update-check failures retain the existing user-visible error state and permit
  retry.
- Manual download remains disabled until an `available` state contains a valid
  semantic version.
- If draft upload partially fails, rerunning the release job updates the same
  draft tag rather than creating a second release.
- The stable release is never published automatically from incomplete native
  jobs.

## Tests

### Unit Tests

- automatic mode enables auto-download/install and retains existing state
  transitions
- manual mode disables auto-download/install, reports availability, and never
  permits `installAndRestart()`
- manual download page requires manual mode plus a valid available version
- canonical release URL construction rejects malformed versions
- title-bar state maps manual availability to an enabled download action
- Settings exposes manual download without Restart & Install
- downloaded banner remains automatic-mode-only
- version consistency validator detects every drifted source
- artifact validator accepts complete Windows/macOS fixtures and rejects
  missing, duplicate, wrong-version, or wrong-reference fixtures

### Build and Release Verification

- `npm run typecheck`
- `npm test`
- `npm run build`
- `npm run build:electron`
- `npm run dist:win` on Windows
- `npm run dist:mac` on macOS
- inspect draft asset list via GitHub API
- download and parse public metadata before publication

## Publication Procedure

1. Merge the release-prep PR to `main` after CI is green.
2. Create and push annotated tag `v2.4.0` from that merge commit.
3. Monitor all release workflow jobs.
4. Inspect the draft release assets and generated notes.
5. Download/parse `latest.yml` and `latest-mac.yml`; verify every referenced
   public draft asset before publication.
6. Publish the draft as stable.
7. Verify GitHub marks v2.4.0 as Latest and every public asset URL resolves.
8. On Windows, verify a v2.3.4 installation discovers/downloads v2.4.0.
9. On macOS, verify a packaged v2.4.0 app reports up to date; preserve the
   manual-mode test coverage for discovery of the next version.

## Rollback

If post-publication checks fail, immediately convert the release back to draft
or delete it so update metadata is no longer discoverable. Fix forward with a
new patch version; never overwrite an already distributed tag or artifact.
Already downloaded unsigned installers cannot be remotely revoked, so release
notes and repository communication must identify any withdrawn build.

## Non-Goals

- Apple Developer ID signing or notarization
- Windows Authenticode signing
- x64/Universal macOS output
- Docker image publication
- automatic macOS self-install while the app is unsigned
